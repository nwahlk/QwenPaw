**需求（REQ）↔ 用户故事（UserStory）↔ API 端点 ↔ 测试用例（TC）**

> 变更需求时，沿链路定位受影响的用户故事、API、测试用例。

## 1. 需求编号体系

| 编号格式 | 含义 | 示例 |
|----------|------|------|
| `需求-M1-{NNN}` | 功能需求 | 需求-M1-001 |
| `规则-{NNN}` | 数据/类型约束规则 | 规则-005 |

| 级别 | 含义 | 门禁影响 |
|------|------|----------|
| **P0** | 必须实现，阻塞发布 | 关联测试用例全绿方可合并 |
| **P1** | 应当实现，不阻塞首版 | CI warning |
| **P2** | 可选增强 | 不纳入门禁 |

### 关键风险

> 列出覆盖率最低的区域及其风险。

| 风险项 | 严重度 | 说明 |
|--------|--------|------|
| JSON 并发写入无锁保护 | 高 | 教学版单用户可接受；生产版须迁移 SQLite/PG（对齐 `08` §5.1 P1），否则数据损坏无 TC 兜底 |
| L4 E2E 测试尚未落地 | 中 | 当前 TC 覆盖到 L3 Contract 层，Playwright E2E 用例（S4 阶段）需在发布前补齐 |
| LLM 幻觉/Prompt 注入仅人工验收 | 中 | `11` §5 定义了验收标准但无自动化 TC，建议 S4 增加 Prompt 注入 Payload 自动化回归 |
